# 블로그 글 리뷰어 개발 후기 글감 메모

후기 글을 쓰기 위한 메모입니다. 진행 순서대로 결정, 오류, 숫자를 모았습니다.
숫자는 실제로 실행해서 나온 값이고, 추정치는 따로 표시했습니다.
이 메모로 포스팅을 쓸 때는 맨 아래 "이미지 목록", "글 구성안", "포스팅 작성 지침"을 따릅니다.

- 기간: 2026-10-07 ~ 2026-10-14
- 방식: 역할·환경·작업 순서를 적은 프롬프트 한 장으로 시작해, Claude Code가 단계마다 실행 결과를 보여주고 내 확인을 받은 뒤 커밋
- 저장소: https://github.com/KiHwanY/blog-reviewer

## 0. 시작 전

### 프롬프트에 비워 둔 칸

LLM, 임베딩, 블로그 플랫폼, 블로그 주소를 대괄호로 비워 둔 채 시작했다. Claude가 1단계 결과와 함께 이 네 가지를 물었다.

- LLM: Claude (`claude-opus-5-5`)
- 임베딩: `bge-m3` (로컬, 무료). OpenAI 임베딩은 API 키가 하나 더 필요해서 뺐다.
- 플랫폼: 티스토리 (https://drg2524.tistory.com)

### 내가 직접 해야 했던 일

- `.env`에 `ANTHROPIC_API_KEY` 넣기 (키 값은 AI가 입력하지 않음)
- 단계마다 결과 보고 "다음" 승인하기
- 크레딧 충전

### 환경

Windows, Python 3.12.10, Docker의 PostgreSQL 16 + pgvector 0.8.6.
다른 프로젝트와 같은 DB를 쓰기 때문에 모든 테이블을 `blog_reviewer` 스키마에만 만들고 `public`은 건드리지 않는다는 규칙을 프롬프트에 넣었다.

## 1단계: DB 연결 확인

- `check_db.py`로 스키마, `vector` 확장, 테이블 생성 권한을 확인했다.
- `.env`의 연결 문자열은 `postgresql+psycopg://`(SQLAlchemy 형식)였다. PGVector는 이 형식을 쓰지만 PostgresSaver처럼 psycopg를 직접 쓰는 곳은 `postgresql://`이 필요하다. 그래서 변환을 `config.py` 한 곳에 모았다.
- 스키마 이름을 코드에 적지 않고, 연결 문자열의 `search_path=blog_reviewer,public`에 맡겼다. 나중에 PGVector 테이블 2개와 체크포인트 테이블 4개가 모두 `blog_reviewer`에 생긴 것을 확인했다.

## 2단계: 블로그 글 수집과 적재

### 수집 방식: sitemap.xml

- 티스토리 공식 Open API는 종료됐고, RSS는 최근 글만 준다.
- `sitemap.xml`에 URL 296개가 있었고 그중 글이 258개, 나머지 38개는 카테고리·홈이었다.
- 글 페이지에서 읽은 위치
  - 제목: `og:title`
  - 작성일: `article:published_time`
  - 카테고리: `.category` (예: `[ ORM ]/JPA`처럼 하위 카테고리까지)
  - 본문: `.contents_style`
- 요청 사이에 1초씩 쉬었다. 258편 수집에 약 11분.
- 수집 결과: 건너뛴 글 0개, 제목·작성일·카테고리가 빠진 글 0개. 본문 길이는 최소 505자, 중앙값 5,109자, 최대 27,358자. 카테고리 23종.

### 분할

- 800자 청크, 100자 겹침 → 청크 3,037개
- 소제목(`##`, `###`)과 코드 블록을 마크다운으로 남겨, 분할기가 소제목 경계에서 먼저 자르게 했다.
- 청크 앞에 글 제목을 붙였다. 800자 조각만으로는 어느 글의 일부인지 알 수 없어서.

### 오류

- **sitemap 파싱 실패**: BeautifulSoup의 `xml` 파서는 `lxml`이 필요했다. 표준 라이브러리 `ElementTree`로 바꿨다.
- **문장이 단어마다 끊김**: 처음에는 모든 태그 경계에서 줄바꿈을 넣어 `지난⏎Loki·Tempo·Alloy⏎시리즈에서는`처럼 굵은 글씨마다 문장이 잘렸다. 블록 태그(`p`, `li` 등)에서만 줄바꿈을 넣도록 고쳤다.
- **표는 못 고침**: 표의 셀이 한 줄씩 떨어져 저장된다. 검색에는 지장이 없다고 보고 그대로 뒀다.

### 임베딩이 오래 걸렸다

- GPU가 없어서 bge-m3가 CPU로 돌았다.
- 첫 시도는 진행이 너무 느려 512개 넣은 상태에서 내가 중단시켰다.
- 재시도 때는 시작부터 Hugging Face 서버 연결이 끊겨 재시도하느라 약 14분이 그냥 지나갔다. 결국 로컬에 받아 둔 모델로 로딩됐다.
- 실제 적재는 초당 약 1청크, 3,037개에 약 55분.
- 적재는 매번 컬렉션을 비우고 전체를 다시 넣는 방식이라, 중간에 멈췄다 다시 돌려도 중복이 생기지 않았다.

## 3단계: 검색 테스트

질문 8개로 상위 결과를 봤다. 숫자는 코사인 거리(낮을수록 가까움).

| 질문 | 1위 글 | 거리 |
|---|---|---|
| JPA에서 N+1 문제는 어떻게 해결해? | [ JPA ] 지연 로딩과 조회 성능 최적화 | 0.364 |
| 스프링 시큐리티로 로그인 구현하는 방법 | [ Security ] 사용자 권한 별 인증 처리하기 | 0.286 |
| 쿠버네티스 클러스터 백업은 어떻게 하지? | [Data Platform] Velero 구축 가이드 | 0.350 |
| SOLID 원칙이 뭐야? | [ Concept ] SOLID | 0.312 |
| 바이브 코딩으로 프로젝트 만든 경험 | 어느 평범한 30대 개발자의 요즘 생각 | 0.371 |
| 무례한 사람을 대하는 방법 | 『무례한 사람에게 웃으며 대처하는 법』 리뷰 | 0.330 |
| How do I ship logs to Loki? (영어) | [Data Platform] Loki 구축 가이드 | 0.375 |
| 김치찌개 맛있게 끓이는 법 (없는 주제) | (무관한 글) | 0.594 |

- **영어 질문으로 한국어 글이 나왔다.** bge-m3의 다국어 성능 덕분.
- **관련 있는 결과는 0.29~0.45, 무관한 주제는 0.59 이상.** 그래서 0.5를 넘는 결과는 버리기로 했다(질문 8개로 잡은 잠정치).
- **한 글이 상위 결과를 독차지했다.** SOLID, Loki 질문은 상위 4개가 전부 같은 글의 청크였다. 리뷰어에게는 여러 글을 근거로 줘야 해서, 청크 20개를 뽑아 글 단위로 묶고 글 4편에서 2개씩 쓰도록 `retriever.py`를 만들었다.
- **바이브 코딩 질문은 아쉬웠다.** 정작 `[Vibe Coding]` 카테고리 글이 2위였다.
- `HF_HUB_OFFLINE=1`을 넣어 모델 로딩 때 서버 확인을 건너뛰게 했다. 8개 질문 테스트가 모델 로딩 포함 36초.

## 4단계: 페르소나와 리뷰 함수

### 구조

- `prompts/common.md`: 모든 리뷰어 공통. 기존 글을 어떻게 근거로 쓰는지, 점수 기준, 출력 형식.
- `prompts/beginner.md`, `senior.md`, `seo.md`: "누구이고 무엇을 보는지"만.
- 점수 기준선을 프롬프트에 적었다. "7점 = 이대로 발행해도 괜찮다". 그래프의 분기 기준(7점)과 리뷰어의 점수 감각을 맞추려고.
- 페르소나마다 "이것은 당신의 관심사가 아니다"를 적어, 세 리뷰가 같은 말을 반복하지 않게 했다.
- 결과는 Pydantic 모델(`score`, `strengths`, `improvements`)로 받는다. Opus 5.5는 도구 호출을 강제하는 방식을 받지 않아서, LangChain 기본값 대신 `method="json_schema"`를 썼다.

### 테스트용 초안

일부러 허술하게 쓴 663자짜리 "pgvector 써본 후기"를 만들었다. 비밀번호 없는 `docker run`, "코사인 유사도라 점수가 높을수록 비슷하다"(실제로는 거리라서 반대), 정의 없는 용어, 반말 말투를 심어 뒀다.

### 결과 (91초)

| 페르소나 | 점수 | 가장 먼저 짚은 것 |
|---|---|---|
| 초보 독자 | 3 | `POSTGRES_PASSWORD`가 없어 그대로 따라 하면 컨테이너가 바로 꺼짐 |
| 시니어 개발자 | 4 | 볼륨도 없어 컨테이너를 지우면 임베딩 3,000개가 사라짐 |
| SEO 전문가 | 4 | 제목에 검색어가 없음. 대안 제목을 직접 제시 |

- 심어 둔 "코사인 유사도" 오류를 초보 독자와 시니어 둘 다 잡았다.
- 기존 글을 근거로 썼다. `[ Docker ] PostgreSQL Docker 볼륨 설정` 글을 링크하라는 제안, 예전 글의 유사도 0.85 기준과 맞추라는 지적이 나왔다.
- 초안은 반말인데 기존 글은 "안녕하세요. 환이s입니다 👋"로 시작하는 존댓말이라는 점도 짚었다.
- 아쉬운 점: 근거로 잡힌 기존 글 4편 중 2편(`게시판 01`, `JSP DB 연결`)은 관련이 약했다.

## 5단계: LangGraph 워크플로우

```
retrieve → 세 페르소나 리뷰(병렬) → synthesize → 평균 7점 미만이면 revise → 다시 리뷰
```

### 결정

- **페르소나마다 노드 하나**: 동적 분기(`Send`) 대신 리뷰 노드 3개를 명시적으로 뒀다. 그래프 이미지에 병렬 구조가 그대로 보인다.
- **리듀서**: 세 노드가 같은 `reviews` 키에 동시에 쓰므로 dict를 합치는 리듀서(`operator.or_`)를 붙였다.
- **평균은 코드로 계산**: 산수는 LLM에 맡기지 않았다.
- **수정 후에는 검색을 다시 하지 않음**: 주제가 같으니까.
- **체크포인터**: PostgresSaver. 나중에 `thread_id`로 결과를 다시 불러오는 데 썼다.

### 오류

- **그래프 이미지 저장 실패**: `draw_mermaid_png()`가 mermaid.ink 서버에 렌더링을 맡기는데 10초 타임아웃에 걸렸다. 재시도 횟수를 5회로 늘려 해결.
- **수정안이 문장 중간에 잘림**: `max_tokens` 16,000에 모델의 생각 분량까지 포함된다는 걸 몰랐다. 2차 수정안이 잘렸고, 잘린 글을 리뷰어가 감점해서 점수가 3.3 → 5.7 → **5.3**으로 오히려 내려갔다. 수정안만 64,000으로 늘리고, 잘리면 오류를 내게 했다.
- **`[확인 필요]` 표시를 감점**: 수정안은 글쓴이만 아는 값(측정값 등)을 지어내지 않고 `[확인 필요: …]`로 비워 두는데, 리뷰어가 이걸 "미완성"이라며 감점했다. 공통 프롬프트에 "채울 자리이니 점수에 반영하지 않는다"를 추가.
- **체크포인트 역직렬화 경고**: 상태에 넣은 Pydantic 모델을 되살릴 때 "등록되지 않은 타입" 경고. 허용 목록을 넘긴 직렬화 설정으로 해결.

### 고친 뒤 결과 (약 8분 30초)

- 점수: 3.3 → 6.7 → 7.0 (2회 수정 후 기준 통과)
- 분량: 663자 → 7,803자 → **16,384자**
- 제목이 "pgvector 써본 후기"에서 "pgvector + LangChain으로 RAG 벡터 검색 구현하기 (bge-m3 한국어 임베딩)"로 바뀌고, 존댓말 인사말과 기존 글 링크가 들어갔다.
- 문제: **수정안이 계속 불어난다.** 리뷰어가 "이것도 설명하라"고 할 때마다 받아 적는다. "범위를 넓히지 말라"는 지시로는 막지 못했다.

## 6단계: Streamlit 화면

- 초안 입력 → 노드별 진행 상황 → 요약 카드(원본·최종 평균, 수정 횟수) → 라운드 선택 → 페르소나 리뷰 3열 → 종합(우선순위 배지) → 수정안 미리보기·내려받기
- **결과를 `st.session_state`에 보관**: 위젯을 건드릴 때마다 스크립트가 다시 실행되므로, 7분짜리 결과를 세션에 넣지 않으면 라운드를 바꾸는 순간 사라진다.
- **주소에 `?thread=<id>`**: 새로고침해도 체크포인트에서 결과를 다시 불러온다. 체크포인터를 붙인 이유를 화면에서 바로 보여주는 기능.
- 화면에서 돌린 결과: 3.3 → 6.3 → 7.0, 663자 → 7,496자 → 12,431자. 약 7분.
- 헛다리: 라운드를 "원본"으로 바꿨는데 점수가 7점으로 보여 버그인 줄 알았다. 다시 렌더링되기 전 화면을 캡처한 것이었다.

## 그 뒤: 비용 문제

### 크레딧이 1달러 남았다

7단계를 마친 뒤 크레딧이 1달러 남은 것을 알았다. 개발하면서 단계마다 실제로 돌려 검증하다 보니 LLM 호출이 46번(전체 워크플로우 3번 포함) 있었다. 실행 전에 비용을 미리 알려 주지 않았다.

### 비용 최적화는 처음에 안 했다

"동작하게 만들기"에만 집중해서 비용은 손대지 않은 상태였다. 그래서 크레딧을 쓰지 않는 것부터 넣었다.

- **사용량 표시**: LLM 호출마다 토큰 수와 예상 비용(토큰 수 × 공개 단가)을 기록해 진행 메시지와 화면에 보여준다.
- **점수가 안 오르면 중단**: 수정 후 평균이 직전보다 오르지 않으면 다음 수정을 건너뛴다. 이 경우 호출이 14회에서 9회로 준다.
- **수정안 분량 목표**: 원본의 2배(최소 3,000자) 안팎.
- 검증은 **가짜 모델**로 했다. 고정된 점수를 돌려주는 가짜 Claude를 끼워 종료 조건 5가지와 사용량 집계를 확인했다. API 호출 0번.

- 출력 단가가 입력의 5배라 비용 대부분이 출력(수정안 본문과 모델의 생각)에서 나온다.

### 실패 한 번에 약 1.3달러 (추정)

- 2차 수정안 호출이 `max_tokens` 64,000을 다 쓰고 잘려 실패했다. 약 10분 걸렸다.
- 응답이 버려져 원인은 직접 못 봤다. "정확히 3,000자를 넘기지 말 것"을 맞추려다 생각이 길어진 것으로 추정.
- 이 호출은 오류로 끝나서 **사용량 기록에 잡히지 않았다.** 표시는 $1.36인데 실제 지출은 약 $2.7로 추정.
- 고친 것
  - 수정안 호출: `max_tokens` 32,000, effort `low`
  - 분량 지시: "넘기지 않는다" → "안팎으로, 글자 수를 셀 필요는 없다"
  - 실패해도 결과 보존: 화면은 실패 전까지의 라운드를 보여주고, 터미널은 `--resume <thread_id>`로 실패 지점부터 이어서 실행
- 체크포인트에서 이어서 돌리니 100초 만에 끝났다. 처음부터 다시 돌렸으면 리뷰 9회를 또 냈을 것.

### 분량 목표의 효과

| | 1차 수정안 | 2차 수정안 | 최종 점수 |
|---|---|---|---|
| 목표 없음 (6단계) | 7,496자 | 12,431자 | 7.0 |
| 목표 3,000자 (10/13) | 3,360자 | 5,169자 | 6.3 (정체로 중단) |

- 크게 줄었지만 2차는 목표의 1.7배.
- 이번에는 7점에 못 미치고 끝났다. 분량을 줄인 탓인지는 한 번의 실행으로는 알 수 없다.

## 그 뒤 2: 로그인 화면과 속도 (10월 14일)

### 로그인 페이지 추가

- 앱을 열면 로그인 화면이 먼저 나오게 했다. 리뷰를 돌릴 때마다 내 크레딧이 나가니 아무나 못 쓰게 막을 필요가 있었다.
- 방식은 두 가지를 놓고 골랐다. Google 로그인(Streamlit `st.login`, 진짜 인증이지만 Google Cloud에서 OAuth 키를 발급받아야 함)과 비밀번호 하나로 잠그기. 혼자 쓰는 도구라 후자를 골랐다.
- `.env`의 `APP_USERNAME`, `APP_PASSWORD` 한 계정만 들어온다. 비교는 `hmac.compare_digest`로 했다. 로그인 상태는 브라우저 세션에만 남아서 새로고침하면 다시 로그인해야 한다.
- 구조: `app.py`는 로그인 여부로 페이지를 고르는 진입점이 되고, 기존 리뷰 화면은 `app_pages/review.py`, 로그인 화면은 `app_pages/login.py`로 옮겼다.

### 모션

- 카드가 아래에서 떠오르며 등장, 배경 빛이 천천히 흐름, 로고가 살짝 떠 있음, 입력칸 포커스 시 빛남, 버튼에 올리면 떠오르고 빛이 지나감, 로그인 성공 후 리뷰 화면 페이드인과 환영 알림.
- **틀리면 카드가 흔들린다.** 실패할 때마다 카드 컨테이너의 `key`를 바꿔(`login_card_shake_1`, `_2`, …) 요소가 새로 만들어지게 해서, 흔들림 애니메이션이 매번 다시 재생된다.
- 운영체제의 "애니메이션 줄이기" 설정을 켠 사용자에게는 모든 움직임을 끈다(`prefers-reduced-motion`).
- `st.html`은 `<svg>` 태그를 걸러낸다. 로고와 아이콘이 통째로 사라져서, SVG를 base64 data URI로 바꿔 CSS 배경 이미지로 넣었다.

### 시안대로 다시 디자인

- 받은 시안을 따라 "편집실" 콘셉트로 바꿨다. 미색 바탕, 짙은 초록(#1E4D3A) 포인트, 명조체(Noto Serif KR) 큰 제목 "신뢰할 수 있는 / 글의 편집실".
- 시안과 다르게 한 것: 이메일 대신 **ID**, 브랜드는 **H 로고 + Hwan_velop**. 시안의 "서비스 소개" 링크와 아래 화살표가 가리킬 곳이 필요해 페이지 아래에 소개 카드 세 장을 새로 만들었다. 카드 아래 ".env 계정만 사용 가능" 문구는 직전에 지워 달라고 한 문구라 넣지 않았다.
- **입력칸 포커스 효과는 첫 버전에서 동작하지 않았다.** Streamlit 1.65의 입력칸에는 `data-baseweb` 속성이 없어서 선택자가 아무것도 잡지 못했다. AI는 CSS가 정의된 것만 보고 "동작한다"고 보고했었다. `[data-testid="stTextInputRootElement"]`로 고치고, 기본 포커스 스타일에 덮이지 않게 `!important`를 붙였다.

### 앱 전체 색감 통일

- `.streamlit/config.toml`에 테마를 만들어 로그인 후 리뷰 화면도 같은 색을 쓰게 했다. 바탕 #FBFAF6, 포인트 초록, 제목은 명조체, 사이드바와 입력칸은 한 톤 진한 베이지.
- 높음·중간 배지와 경고·안내 상자 색은 의미를 유지하되 채도를 낮췄다. 파란 안내 상자는 청록으로 바꿨다.

### 로그인 화면이 늦게 뜨는 문제 (원인을 찾기까지 네 번)

"로그인 창이 너무 늦게 나온다"는 지적에서 시작했다. 원인을 바로 못 찾고 여러 번 헛짚었다.

| 순서 | 가설과 조치 | 결과 |
|---|---|---|
| 1 | `auth.py`가 `config.py`를 불러와 LLM·임베딩 라이브러리까지 로딩함 → `.env`만 직접 읽게 바꿈 | 로그인 모듈 로딩 4.6초 → 1초. 이건 실제 개선 |
| 2 | 로그인 직후 리뷰 화면이 5초 걸림 → 로그인 화면이 뜨고 1.5초 뒤 리뷰 화면 모듈을 미리 불러 둠 | 로그인 후 전환은 빨라졌지만, 4번의 문제를 로그인 화면까지 끌고 옴 |
| 3 | 로그인 화면 CSS의 글꼴 `@import`가 화면을 막음 → 제거하고 테마가 글꼴을 불러오게 함 | AI가 "0.3초로 빨라졌다"고 보고. 그런데 **상단 문구만 재고 로그인 카드는 재지 않았다** |
| 4 | 사용자가 "실행 중 아이콘이 돌 때까지 카드가 안 나온다"고 짚어 줌 → 서버 로그에서 진짜 원인 발견 | 카드 4.4~9초 → **0.37~0.5초** |

- **진짜 원인**: Streamlit의 파일 감시 기능(코드가 바뀌면 자동으로 다시 불러오기)이 화면을 그릴 때마다 메모리의 모든 모듈을 훑는다. `transformers`를 훑을 때마다 쓰지도 않는 이미지 처리 모듈을 불러오려다 실패해서(`No module named 'torchvision'`, 로그에 40번) 매번 몇 초씩 걸렸다. 서버는 화면 내용을 0.006초 만에 만들어 놓고도 이 작업 때문에 실행 표시가 계속 돌았다.
- **해결**: `.streamlit/config.toml`에 `fileWatcherType = "none"`. 대신 코드를 고친 뒤에는 앱을 다시 켜야 반영된다.
- **헛짚은 것**: 3번 뒤 AI는 "테스트용 브라우저 창이 숨겨져 있어서 화면 갱신이 멈춘 탓"이라고 추정했는데 틀렸다. 같은 숨겨진 창에서 4번 수정 후에는 0.4초 안에 떴다.
- 고친 뒤 측정: 접속 → 로그인 카드 0.37~0.5초, 로그인 버튼 → 결과 화면 0.45초, 라운드 전환 0.52초.

### 실제 테스트 리뷰 (Spring 초안)

블로그에 Spring 글이 많아 근거가 잘 잡히도록 "@Transactional 안 될 때"라는 763자 초안을 만들어 화면에서 돌렸다. 틀린 설명 두 개("private 메서드에도 잘 동작한다", "모든 예외에서 롤백한다")와 반말, 원인 설명 없는 결론을 심어 뒀다.

| 항목 | 값 |
|---|---|
| 점수 | 2.7 → 6.0 → 7.0 (2회 수정 후 기준 통과) |
| LLM 호출 | 14회, 입력 약 11.5만 / 출력 약 3.9만 토큰, 약 1.25달러 |
| 분량 | 763자 → 4,818자 → 5,483자 (목표 약 3,000자) |
| 남은 `[확인 필요]` | 5곳 (Spring Boot 버전 등) |

- 심어 둔 문제는 모두 잡았다. 시니어 개발자는 private 메서드와 내부 호출(self-invocation), 체크 예외 롤백 규칙을 짚었고, SEO 전문가는 대안 제목을 냈다.
- 심어 두지 않은 문제도 하나 찾았다: `throw new Exception(...)`을 쓰려면 `throws Exception` 선언이 필요해 예제가 컴파일되지 않는다.
- 최종 제목: "[ Spring ] @Transactional 롤백 안 될 때 - private, 내부 호출, Checked Exception 원인 3가지". 존댓말로 바뀌었다.
- 아쉬운 점: 근거로 잡힌 기존 글이 Bean Validation, Component Scan, 예외 처리 글이었다. 블로그에 트랜잭션을 직접 다룬 글이 없으면 이렇게 된다.

## AI가 한 실수

후기에서 솔직하게 쓸 만한 것들.

- **`.gitignore` 두 줄을 한 줄로 붙임**: 파일 끝에 줄바꿈이 없는 걸 모르고 `data/`를 덧붙여 `__pycache__/data/`가 됐다. 두 규칙 모두 동작하지 않았다. push 직후 발견해 바로 고쳤고, 그 사이 잘못 커밋된 파일은 없었다.
- **같은 문법 오류를 두 번**: 셸에서 파이썬 스크립트로 코드를 고치다가 `\n`이 실제 줄바꿈으로 바뀌어 f-string이 깨졌다. 두 번 다 바로 고쳤다.
- **실행 횟수를 잘못 셈**: 비용을 추정하면서 전체 워크플로우를 4번 돌렸다고 했다가, 다시 세어 3번으로 정정했다.
- **비용을 미리 말하지 않음**: 검증하라는 요청대로 돌렸지만, 한 번에 1~2달러 드는 실행 전에 금액을 알렸어야 했다.
- **실패한 호출은 사용량에 안 잡힘**: 사용량 표시를 만들 때 놓친 부분. 실제로 비싼 실패를 겪고 나서야 알았다.
- **동작하지 않는 효과를 동작한다고 보고**: 로그인 입력칸 포커스 효과. CSS가 있는 것만 보고 실제 적용을 확인하지 않았다.
- **엉뚱한 요소로 속도를 잼**: 로그인 화면 속도를 상단 문구로 재고 "0.3초로 빨라졌다"고 보고했다. 사용자가 기다리는 건 로그인 카드였다.
- **원인을 잘못 추정**: "숨겨진 브라우저 창 때문"이라고 했다가, 사용자가 짚어 준 실행 표시를 단서로 진짜 원인(파일 감시)을 찾았다.
- **자기가 넣은 기능이 문제를 키움**: 리뷰 화면 미리 불러오기가 `transformers`를 로그인 단계부터 올려, 파일 감시 문제를 로그인 화면까지 끌고 왔다.

### Intro

- 인사말, 이 글이 무엇인지(바이브 코딩으로 만든 블로그 글 리뷰어의 개발 후기).
- 만든 이유: 발행 전에 "처음 보는 사람이 이해할까, 틀린 내용은 없을까, 검색에 걸릴까"를 혼자 점검하기 어려웠다.
- 이 글에서 다룰 내용 목록.
- 이전 글 [[Vibe Coding] 지역 블로그 AI 에이전트 구축기 (feat. Claude + pgvector)](https://drg2524.tistory.com/259)와 이어지는 시리즈라는 점.

### 1. 무엇을 만들었나

- 초안을 넣으면 내 기존 글 258편을 근거로 세 리뷰어(초보 독자, 시니어 개발자, SEO 전문가)가 리뷰하고, 종합해서 수정안까지 만드는 도구.
- [이미지: 01-input.png] 캡션: 초안을 붙여 넣고 리뷰 시작을 누르면 된다.
- [이미지: 07-passed.png] 캡션: 허술한 샘플 초안이 두 번 고쳐져 3.3점에서 7.0점이 됐다.
- 기술 스택 표(README의 표를 줄여서): LangGraph, LangChain, PostgreSQL + pgvector, Claude Opus 5.5, bge-m3, Streamlit.

### 2. 진행 방식

- 프롬프트 한 장(역할, 환경, 절대 지킬 것, 작업 7단계)으로 시작.
- 단계마다 실행 결과를 보고 승인하면 그 단계를 커밋.
- 내가 직접 한 일: API 키 넣기, 단계별 승인, 크레딧 충전. 나머지(코드, 설치, 실행, 커밋)는 AI.
- 비워 둔 칸(LLM, 임베딩, 플랫폼, 주소)을 AI가 먼저 물어봤다.

### 3. 내 블로그 글을 RAG로 넣기

- sitemap.xml로 258편 수집. RSS는 최근 글만 줘서 뺐다.
- 800자 청크 3,037개, 청크 앞에 글 제목 붙이기.
- GPU 없이 CPU로 임베딩 약 55분. 그 전에 Hugging Face 연결 문제로 14분을 그냥 날렸다.
- 검색 테스트 표(질문 8개). 영어로 물어도 한국어 글이 나왔다.
- 한 글이 상위 결과를 독차지하는 문제 → 글 단위로 묶어서 4편에서 2개씩.

### 4. 리뷰어 세 명 만들기

- 공통 프롬프트 + 페르소나 프롬프트로 나눈 이유. 7점 = "이대로 발행해도 괜찮다" 기준선.
- 일부러 허술하게 쓴 663자 샘플 초안(심어 둔 오류 목록).
- [이미지: 04-reviews.png] 캡션: 같은 초안을 세 리뷰어가 각자 다른 곳을 짚는다.
- 심어 둔 "코사인 유사도" 오류를 두 리뷰어가 잡았고, 기존 글과 말투가 다르다는 것도 짚었다.

### 5. LangGraph로 리뷰 흐름 묶기

- [이미지: graph.png] 캡션: 검색 → 세 리뷰 병렬 → 종합 → 7점 미만이면 수정 후 다시 리뷰.
- 페르소나마다 노드 하나, 리듀서, 평균은 코드로 계산.
- [이미지: 05-synthesis.png] 캡션: 세 리뷰를 우선순위별 수정 사항으로 정리한 결과.
- [이미지: 06-revised.png] 캡션: 수정안. 내가 직접 채워야 할 곳은 `[확인 필요]`로 남긴다.
- 체크포인터: 새로고침해도 결과가 남고, 실패해도 이어서 실행할 수 있다.

### 6. 삽질

- 수정안이 `max_tokens`에 걸려 잘림 → 잘린 글을 감점해서 점수가 오히려 내려감(5.7 → 5.3).
- 수정안이 계속 불어남: 663자 → 16,384자.
- `[확인 필요]` 표시를 리뷰어가 감점.
- AI가 한 실수들(`.gitignore` 줄 붙음, 같은 문법 오류 두 번, 실행 횟수 오산).

### 7. 비용

- 7단계를 다 끝내고 보니 크레딧이 1달러 남았다. 비용 최적화는 처음에 안 했다.
- 사용량 표시, 점수 정체 시 중단, 분량 목표를 넣었다. 검증은 가짜 모델로 해서 비용 0원.
- [이미지: 02-summary.png] 캡션: 결과 화면에 예상 비용이 같이 나온다.
- [이미지: 03-usage.png] 캡션: 호출별 토큰 수. 비용 대부분이 출력에서 나온다.
- 호출별 실측 비용표(위 "충전 후 실제 테스트" 표).
- 실패 한 번에 약 1.3달러(추정), 그 실패는 사용량 표시에 안 잡혔다. 고친 방법과 체크포인트로 이어서 실행해 100초 만에 끝낸 이야기.
- 분량 목표 전후 비교표.

### 8. 대표 화면: 로그인과 모션

- 크레딧이 나가는 도구라 로그인으로 잠갔다. 비밀번호 하나로 잠그는 간단한 방식을 고른 이유.
- [이미지: 08-login.png] 캡션: 시안을 바탕으로 만든 "편집실" 로그인 화면.
- 모션 목록과 "틀릴 때마다 key를 바꿔 흔들림을 다시 재생"하는 요령. `st.html`이 SVG를 걸러내 CSS 배경으로 우회한 이야기.
- [이미지: 09-shake.png] 캡션: 비밀번호가 틀리면 카드가 흔들린다. (선택)
- 로그인 화면이 늦게 뜬 문제를 네 번 만에 찾은 과정(표). 진짜 원인은 Streamlit 파일 감시였다.
- 앱 전체 색감을 테마 설정 하나로 맞춘 것.

## 포스팅 작성 지침

이 메모를 받아 블로그 글을 쓸 때 지킬 것.

- **블로그**: 티스토리 https://drg2524.tistory.com, 카테고리 `[ Vibe Coding ]`.
- **제목 형식**: 기존 글처럼 `[Vibe Coding] ○○○ 구축기 (feat. ○○)` 형태. 예: `[Vibe Coding] 내 블로그를 아는 AI 글 리뷰어 구축기 (feat. LangGraph + pgvector)`
- **말투와 구성**: 존댓말. `### Intro`로 시작해 "안녕하세요. 환이s입니다 👋" 인사말을 쓰고, 본문 소제목은 `### 1. …`, `### 2. …`처럼 번호를 붙인다. 위 "글 구성안"의 순서를 따른다.
- **사실만 쓴다**: 숫자와 사건은 이 메모에 있는 것만 쓴다. 메모에 "추정"이라고 적힌 값은 본문에서도 추정이라고 밝힌다. 메모에 없는 성과나 경험을 지어내지 않는다.
- **이미지**: 이미지는 글쓴이가 직접 넣는다. 구성안의 `[이미지: 파일명]` 자리에 같은 표시를 그대로 한 줄로 남기고, 바로 아래에 캡션을 한 줄 쓴다. 이미지 링크(`![](...)`)는 만들지 않는다.
- **코드**: 긴 코드는 넣지 않는다. 핵심 몇 줄(그래프 연결부, 프롬프트의 점수 기준 문장 등)만 인용하고 나머지는 저장소 링크로 안내한다.
- **분량**: 후기이므로 튜토리얼처럼 모든 단계를 재현하게 쓰지 않는다. 결정과 이유, 삽질, 숫자에 집중한다.
- **"아직 못 한 것"은 숨기지 않는다**: 실제 내 초안으로 돌려 보지 않았다는 점은 마무리에서 밝힌다.
